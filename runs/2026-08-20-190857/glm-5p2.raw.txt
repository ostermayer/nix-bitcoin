## Investigation summary

**Attack surface mapped.** This fork ships a trimmed service set: `bitcoind`, `lnd`, `electrs`, `btcpayserver`/`nbxplorer`, plus `lndconnect`, onion services, netns isolation, secrets setup, operator, and the `wireguard`/`secure-node`/`hardened` presets. I focused where funds/keys/cross-service boundaries live: `lnd.nix` (macaroons, seed, wallet password), `secrets/secrets.nix` (permissioning), `bitcoind.nix` (cookie + RPC whitelist), `onion-addresses.nix` (the historical symlink-privesc spot, heavily hardened here), and `netns-exec` (cap_sys_admin wrapper).

**What I checked and ruled out (no finding):**
- Secrets-in-store: every `cat ${secretsDir}/...` is inside a runtime `preStart`/`script` body; the stored `writeText`/`toFile` artifacts contain only paths/usernames/HMACs, never secret values. No leak.
- File perms on secrets: `setup-secrets` chowns per-secret with `umask u=rw,go=`, then `chmod 0751` the dir (traverse-only for "other"); unprocessed files fall back to `0440 root:root`. Tight.
- RPC whitelist: `public`/`btcpayserver` users inherit the curated public list (no wallet calls, no `setban`/`generatetoaddress`/`getblockfrompeer`); `rpcwhitelistdefault=0` only grants full access to `privileged` (HMAC root-only). Correct.
- Group boundaries: no LN/electrs/btcpay service joins the `bitcoin` group, so the group-readable privileged `.cookie` is reachable only by `bitcoind` + the trusted `operator` (the documented L-10 accepted risk). Minimal.
- lnd macaroon *creation* race: the root-only `mktemp -d` staging + atomic `mv -f` (rename, no dst-symlink follow) correctly closes the write-time race the comment describes.
- netns-exec: hardcoded allowlist, absolute-path exec, drops all caps after `setns`, mode 500 owner=operator. Clean.
- Supply chain: nixpkgs via flake.lock `narHash`, krops pinned by commit+sha, lndinit/nbxplorer pinned hashes, `fetch-release` refuses upstream unless overridden. Clean.
- backups.nix: I initially suspected the encryption passphrase was bundled in the encrypted backup. It is, but it is encrypted by itself, so an attacker holding only the backup blob cannot decrypt it. **False positive, dropped.**

**What survived scrutiny (two findings):**

1. The lnd macaroon hardening closes only the *write-time* race. The final macaroon is placed into `$RUNTIME_DIRECTORY` (`/run/lnd`), which **lnd owns** (line 265 admits this). After the one-shot `ExecStartPost`, a compromised lnd can replace `/run/lnd/btcpayserver.macaroon` with a symlink to any btcpayserver-readable file. btcpayserver (which starts *after* lnd) reads that path as its macaroon and ships the bytes hex-encoded to lnd's REST endpoint on every RPC — a clean cross-service secret-exfiltration primitive from a single compromised service.

2. `onion-addresses.nix` `copyOnionFile` does a non-atomic `[[ -L $src ]]` check then `install -T` (which follows symlinks), in a root service holding `CAP_DAC_OVERRIDE`/`CAP_DAC_READ_SEARCH`. A compromised tor user can race the check at tor-restart and make root copy an arbitrary file into a service's onion-address slot. The high-value payoff is limited (the destination is owned by another principal, so no direct exfil-to-attacker; realistic solo outcome is corrupted onion address → DoS/privacy via a blind race). Lower confidence.
