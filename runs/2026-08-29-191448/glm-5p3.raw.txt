The audit is complete. Here is the report.

## Surface map

Commit `19517ec` is the trimmed fork: `bitcoind`, `lnd` (+`lndinit`, `lndconnect`), `electrs`, `btcpayserver`/`nbxplorer`, plus infra (secrets, operator, onion-addresses/services, netns-isolation, nodeinfo, backups, presets, deployment) and packaging (netns-exec, krops, overrides). Deltas since the last audited commit (`17c07ac`): the four finding fixes of `121406c` (onion hostname validation, cookie 0640, electrs.toml 600), the CVE-whitelist collision triage `a6dbbd8`, the pin bump `312e384`, the update-flake.sh guard fix `821b5e8`, the wireguard REST-bind deferral doc `19517ec`, and audit-infra/CI commits that carry no node code. The fork also runs a weekly vulnix CVE scan of a representative node's closure (new machinery since the last audit, which is where both new defects live).

## Investigation and verdicts

**The 121406c fixes are sound.** The onion hostname regex `^[a-z2-7]{56}[.]onion$` is a correctly anchored bash ERE with no Nix antiquotation hazards; command substitution strips the trailing newline (real Tor output passes) and drops NUL bytes, and since the output is written from the validated copy, no NUL-smuggling or second-line injection can reach the `externalip=$(cat …)` / `--host=$(cat …)` splices. I traced every splice consumer: each reads the copy in `/var/lib/onion-addresses` owned by its own user, so rewriting it is self-injection only. The tor user cannot write any output dir. The check-then-read TOCTOU claim holds: any raced-in symlink content still has to match the onion shape. `install -T` unlinks a pre-existing destination, output dirs are root-built 0700/0755 and chowned last, all chowns use `-h`.

**Cookie and electrs fixes verified, and the cookie fix is CI-asserted** (`tests.py` asserts stat 640 on `.cookie`). electrs.toml now matches the lnd/nbxplorer `install -m 600` pattern.

**btcpayserver credential scope (prior medium): fixed.** The `setban`/`generatetoaddress` over-grants are gone; the btcpayserver RPC user inherits only the public read/relay whitelist, so the residual group-sharing of nbxplorer's password no longer reaches any node-control RPC.

**Supply chain unchanged and clean.** flake inputs rev-locked with narHash; lndinit/nbxplorer hash-pinned; krops pinned to a commit; `fetch-release` still refuses upstream without an explicit env override and GPG-verifies; `overrides.nix` empty and inert; workflows use SHA-pinned actions.

**a6dbbd8 collision triage:** mechanism verified against vulnix's actual source — per-CVE `cve = [...]` whitelisting is real, and fully-whitelisted derivations are omitted from JSON entirely. The pre-2026 CVE claims (Jenkins git-plugin, Plotly dash, knp-snappy, Nix-manager FOD bypass) check out against my knowledge. The two 2026 `uuid` CVEs I could not verify offline; the claim structure is specific and plausible, filed as accepted.

**The new defect territory, the CVE-scan pipeline, failed verification twice.** Reading vulnix's source (`output.py`, `main.py`, `whitelist.py`, `nvd.py`) settled two things the script gets wrong. First, in vulnix's JSON, `affected_by` lists only *active* CVEs and `whitelisted` lists the *masked* ones, so the script's `whitelisted | length == 0` conjunct drops any derivation that has both collision CVEs whitelisted and a live CVE, the exact scenario the per-CVE scoping policy was written to catch. I confirmed with a jq simulation: git carrying a real future CVE alongside the six whitelisted Jenkins CVEs reports count 0, "clean", and the workflow closes the tracking issue. Second, every vulnix error path (NVD fetch failure via `raise_for_status`, whitelist TOML parse error raised as RuntimeError, exit 2) produces empty stdout, which the script converts to `[]`, and `jq … || echo 0` converts any invalid JSON to zero findings; `rc` is captured and printed but never acted on. A broken scan is indistinguishable from a clean scan and actively closes the tracking issue.

**Known residuals re-checked.** The NoBan whitelisted localhost socket (electrs/btcpayserver set `listenWhitelisted = true`, so bitcoind `whitebind`s 127.0.0.1:8335 with NoBan semantics for any local user) is still present, unfixed and undocumented, having been reported in the 2026-08-20 run. The wireguard preset's `restAddress = "0.0.0.0"` is now a consciously documented deferral; I verified the deferral doc's six breakage vectors against the code (nbLib.address mapping, cert SANs, ExecStartPost curl, btcpayserver lnd-rest, lndconnect onion target, nodeinfo) and they are accurate, so I file it as info, not as an open defect.

Everything else previously verified clean at `17c07ac` was re-spot-checked and is unchanged: lnd macaroon staging (root-only mktemp dir, atomic rename, fd-passed macaroon), secrets generation/permission flow, netns matrix and netns-exec hardening, RPC whitelists, trim cleanliness, and test coverage.
