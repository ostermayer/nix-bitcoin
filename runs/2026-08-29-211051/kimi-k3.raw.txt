## Re-verified earlier fixes (spot-checked at HEAD)

Onion-hostname content validation (`^[a-z2-7]{56}[.]onion$`) genuinely fails closed: bash ERE without REG_NEWLINE anchors `^`/`$` at string ends, so multi-line config injection can't pass, and read-once closes the symlink TOCTOU. Macaroon staging in a root-only `mktemp -d` on the same tmpfs + atomic `mv` closes the lnd-writable-dir race. `netns-exec`: absolute-path required, netns whitelist exact-match, caps dropped before `execv`, owner-only 0500. Secrets: no argv passwords (rpcauth via fd/file), `escapeShellArg` everywhere, unlisted files locked to root:0440. The `jq -c '.macaroon' | xxd -p -r` macaroon pipeline looks wrong (lnd REST looks like base64) but lnd hex-encodes this field and the btcpayserver VM test exercises it end-to-end (`xxd -ps` the file, authenticated `/v1/getinfo`) — verified working, not a bug.

## New findings

Nothing critical or high. Four low/informational items, all in the fork's own code/docs:

1. **Low, known-open**: wireguard preset binds lnd REST to `0.0.0.0` with firewall-only protection, and the accept rule matches `-s 10.10.0.0/24` without `-i wg-nb`. With loose `rp_filter` a spoofed-source packet on the external interface passes the rule, but TCP can't complete a blind handshake, so practical impact is near nil. Extensively documented in `docs/wireguard-rest-bind.md`; the deferral is justified.
2. **Info (CI hygiene)**: `.github/workflows/test.yml` has no top-level `permissions:` block, unlike `cve-scan.yml` (`contents: read` + scoped `issues: write`) and `release-tag.yml` (`contents: write`, justified). The job never uses `GITHUB_TOKEN`, so `permissions: contents: read` would just match the repo's own posture.
3. **Info (trim residue)**: `mkCliExec` in `modules/netns-isolation.nix:98` is dead since the cliExec removal; `examples/deploy-krops.sh` and `examples/deploy-container.sh` still run `lightning-cli` (removed with clightning), so the demos print a failing command; `SECURITY.md` still references the deleted `helper/push-release.sh`. For a fork whose security model is "delete aggressively," leftovers are the trim's failure mode.
4. **Info (docs)**: `docs/configuration.md` demonstrates `rpc.address = "0.0.0.0"` with `rpc.allowip = [ "0.0.0.0/0" ]` without noting that the `public` RPC user (whose whitelist intentionally retains `getpeerinfo`/`getnodeaddresses`) then becomes reachable at whatever scope the operator's firewall allows. HMAC + 119-bit passwords keep this from being blatantly insecure; a one-line caveat would close it.
