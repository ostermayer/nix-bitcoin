# Security audit — ostermayer/nix-bitcoin fork @ c021a3e441a3b7c21c2a75fe28d3f17f01fcdebd

## Surface map

The fork ships NixOS modules (not a flat package set), so the deployed attack surface is what the recommended preset builds. I mapped it as:

- **Secrets pipeline** (`modules/secrets/secrets.nix`): generation (pwgen, openssl, rpcauth via file not argv), root `setup-secrets` service, deployment via krops/nixops.
- **Root-privileged helpers**: `setup-secrets`, lnd macaroon `ExecStartPost` root script, `onion-addresses` service, netns setup services, `netns-exec` (C, cap_sys_admin wrapper).
- **Services**: bitcoind, lnd, electrs, nbxplorer, btcpayserver, postgres, duplicity. All under `nbLib.defaultHardening`, dedicated users, localhost/netns binds.
- **Exposure paths**: onion services (sshd, bitcoind, electrs, btcpay, lnd-rest), the wireguard preset (lnd REST on 0.0.0.0), the bitcoind public RPC whitelist.
- **Supply chain**: flake.lock pins (nixpkgs 26.05 @ 93108a5, 2026-09-07), `pkgs/overrides.nix` security bumps, hash-pinned fetches, weekly vulnix scan of the runtime closure, CI VM suite, release tagging.

I resolved the actual deployed closure by evaluation: bitcoind 31.1, lnd 0.21.3-beta, btcpayserver 2.4.3 (override active), nbxplorer 2.6.10, electrs 0.11.0, tor 0.4.9.11, postgresql 17.11, openssh 10.5p1, systemd 260.2, kernel 6.18.49.

## Verified good (prior fixes hold)

The two hardening commits (d22c5da, c021a3e) were the prime suspects for incomplete fixes. All of their claims check out:

1. **lnd macaroon delivery** is now genuinely tight: staging in a root-only `mktemp -d /run/lnd-macaroons.XXXXXX` (lnd cannot enter /run itself), final delivery via atomic `mv -fT` rename that replaces a planted symlink instead of following it, `admin.macaroon` read as the lnd user via `runuser` so a planted symlink fails closed, 64 KiB cap on the lnd-controlled REST body, and `jq -ce` fail-closed that actually works because `nbLib.script` sets `pipefail`. There is even a runtime regression test (`lnd-macaroon-read-deprivileged` in tests.py) that proves the read-as-lnd asymmetry with a canary file.
2. **setup-secrets sandbox**: `ProtectSystem=strict` with only the secrets dir writable, no network (AF_UNIX), `NoNewPrivileges`, capability set limited to chown/fowner/dac. The `+` prefix semantics work in its favor where needed.
3. **wireguard rule ordering**: `-I nixos-fw 1` / `-I FORWARD 1` now precede the appended accept rules, and the REST accept is pinned to `-i wg-nb` plus the single peer /32. Reply traffic to server-initiated connections survives because its destination is serverAddress.
4. **onion-addresses**: refuses symlinked hostname files, validates content as exactly one v3 onion address (load-bearing: those bytes are spliced into `externalip=` config lines, so this blocks config injection), builds output dirs as root and chowns last, `chown -h` throughout.
5. **netns-exec**: absolute-path `execv`, capability return checks, nonzero exit on exec failure; wrapper is owner-only 0500.
6. **CVE scan tooling**: scans the real recommended deployment's runtime closure (secure-node plus all services plus backups), fails closed on malformed reports and counting errors, and the whitelist entries are narrowly scoped per-CVE for name collisions.
7. **Version pinning**: overrides are wired with correct precedence (`overrides > self > pinned`) and the btcpayserver 2.4.3 override demonstrably reaches the deployed closure. bitcoind and lnd are at upstream latest.
8. No secrets land in the nix store; source fetches are hash-pinned and HTTPS-only; no curl-to-shell anywhere; the only `--insecure` in the tree is a test client; the upstream fetch-release helper refuses to run without an explicit override.

## Findings

**1. tor 0.4.9.11 misses security release 0.4.9.12 (medium).** Released 2026-09-08, one day after the pin and one day before this HEAD. Upstream calls it "another security release containing several high security fixes... We very strongly recommend upgrading as soon as possible." Client-relevant fixes include a hostile directory cache tricking the client into treating relay descriptors as unusable (TROVE-2026-034), a consensus-diff memory DoS class (TROVE-2026-042), and a UAF (TROVE-2026-043). tor is the largest continuously exposed parsing surface on the recommended node: all service traffic is proxied through it and it terminates inbound connections for five onion services. The weekly vulnix scan cannot catch this: tor tracks advisories as TROVE IDs, not NVD CVEs. The audit doc's subscription list (section 5) recommends feeds for Core, lnd, CLN, clboss, btcpay, RTL, but no tor feed. Fix: a version-guarded `pkgs/overrides.nix` entry for 0.4.9.12, and add tor-announce to the maintenance feeds.

**2. btcpayserver 2.4.3 lags security release 2.4.4 (medium).** Released 2026-09-07 (same day as the pin). Upstream: "a new security-focused update that continues our work to harden the codebase... strengthens permissions and validation around invoices, API keys, server administration and other sensitive operations. We recommend that all server administrators update." The fork's own overrides.nix was written for 2.4.3 and pins exactly that, so the recommended deployment runs an internet-facing payment processor one security release behind. Same blindness as finding 1: no CVEs assigned. Fix: bump the override and regenerate the nuget lockfile per the documented procedure in pkgs/btcpayserver/default.nix. Context I verified: the in-the-wild `/lnd-rest/btc/v1/changepassword` attack described in the 2.4.4 post does not apply to this fork's shape, because lnd REST is never reverse-proxied publicly here and the wallet uses a per-node random password with startup auto-unlock. The gap is the application-layer fixes, not that endpoint.

**3. wireguard preset binds lnd's admin REST to 0.0.0.0 with firewall-only protection, but never asserts the firewall is enabled (medium-low).** I confirmed in the pinned nixpkgs that the entire firewall module config, including `extraCommands` and `allowedUDPPorts`, sits behind `mkIf cfg.enable`. The preset's only assertion is the netns incompatibility check. A user config with `networking.firewall.enable = false` (common in VMs, containers, or behind an upstream firewall) gets the macaroon-admin REST API listening on every interface with no accept rule and no default-drop, and the preset evaluates cleanly. This compounds the already-tracked, deferred 0.0.0.0 bind in docs/wireguard-rest-bind.md. A one-line assertion (`networking.firewall.enable` when the wg lndconnect mode is active) is independent of the deferred rebind work and should land now.

**4. no release-gating CI coverage for the wireguard preset (low).** The CI matrix is default/regtest/netns; test/ci/test-info.nix parses that list straight out of test.yml. `wireguard-lndconnect` exists only in run-tests.sh's local buildable list. The firewall rule fixes in this very commit (c021a3e) therefore have no regression protection on the path that gates the release branch. Add the scenario to the matrix.

**5. dead code: fetchNodeModules (info).** `pkgs/build-support/fetch-node-modules.nix` survived the RTL removal; nothing consumes it except its own wiring in pkgs/default.nix, and the flake already strips it from exports. Build-time-only surface, but it is exactly the bloat the fork's own policy says to delete.

Nothing else rose to finding level. The operator privilege model (cookie group access, doas to lnd) is documented by design. The public RPC whitelist is properly trimmed. The committed example VM key is upstream's standard throwaway demo key, dev-only.
