# Security audit — ostermayer/nix-bitcoin @ 8c86b91 (2026-08-29 follow-up)

## 1. Surface map and focus

The fork ships: `bitcoind`, `lnd` (+`lndinit`, `lndconnect`), `electrs`, `btcpayserver`+`nbxplorer`, and infrastructure (`secrets/`, `operator`, `onion-*`, `netns-isolation`, `security`, `nodeinfo`, `backups`, presets incl. `wireguard`, `bitcoind-remote`). I prioritized by where funds/keys/root are reachable:

1. **Secrets plumbing** (`modules/secrets/`, every preStart that cats a secret, every `chmod/chown/install`) — highest value.
2. **Root-privileged activation contexts** (`+`-prefixed ExecStartPost scripts, `setup-secrets`, `onion-addresses`, the wireguard peer script) — the historical bug class in this repo.
3. **lnd macaroon lifecycle** — fixed twice before (b2eb47f write path, 9b71bec), so I re-audited the whole script rather than trusting the fixes.
4. **RPC whitelisting, privilege boundaries, network defaults, supply chain** (fetchers, CI, `overrides.nix`, `pinned.nix`).

## 2. Verified clean (read the code, not guessing)

- **No secret values reach the store.** Every `writeText`/`toFile` config (`lnd.conf`, `bitcoin.conf`, btcpay/nbxplorer configs, backups filelist, nodeinfo) contains only paths and non-secrets; passwords/HMACs are appended at runtime into service-owned files (`install -m 600/640`). RPC password reaches `rpcauth.py` via file, not argv (secrets.nix:83-91).
- **onion-addresses (root, CAP_DAC_OVERRIDE)**: the 2026-08-24 fix holds — symlink-refusing read, read-once-into-variable, strict `^[a-z2-7]{56}[.]onion$` content validation before any splice into `bitcoin.conf`/`lnd.conf`/lndconnect, fail-closed. Write side: root-built 0700 dirs, `chown -h`, populate-then-hand-over. `rm -rf -- ./*` in a root-only dir; rm doesn't follow symlinks on delete.
- **RPC whitelist**: dangerous methods trimmed with documented rationale; `getpeerinfo/getnodeaddresses` retention is justified (lnd health check) and documented. btcpayserver's RPC user inherits the public whitelist (the `setban`/`generatetoaddress` over-grants were removed in be5e094).
- **Privilege boundaries**: `netns-exec` wrapper is owner-only 0500 + `cap_sys_admin=ep`, absolute-path execv, caps dropped, netns whitelist matches shipped services. Supplementary groups are minimal per service (`bitcoinrpc-public` for RPC consumers; cookie group `bitcoin` = operator only, documented). doas/sudo rules are the standard operator pattern.
- **systemd hardening**: `defaultHardening` applied to every daemon; the only unsandboxed units are by-design root oneshots (`setup-secrets`, netns setup, onion-addresses with explicit capability carve-outs).
- **Supply chain**: every fetcher hash-pinned; krops pinned to a commit hash; `fetch-release` refuses upstream tarballs by default and GPG-verifies against a pinned fingerprint; CI actions pinned by SHA; `cve-scan.sh` fails closed on build/JSON errors (1caa0af verified in place); `overrides.nix` version-guarded.
- **Electrs/lnd/btcpay ordering**: `wants`-not-`requires` choices are deliberate and commented (cascade-stop avoidance); secrets target ordering is correct (`requiredBy`/`before`, services `after`).

## 3. Finding: the macaroon script's READ path survived two fixes of the WRITE path

`modules/lnd.nix:262-288` — `ExecStartPost` runs `lnd-create-macaroons` via `nbLib.rootScript` (pkgs/lib.nix:88 = `"+"` prefix): unsandboxed real root, all namespace/filesystem restrictions bypassed. Commits 9b71bec and b2eb47f hardened the write/chown side (root-only staging + atomic `rename`). But line 280 still has root **reading** through an lnd-controlled path with no guard:

```
adminMacaroonHex=$(${pkgs.xxd}/bin/xxd -ps -u -c 99999 '${networkDir}/admin.macaroon')
```

`/var/lib/lnd` is `0770 lnd:lnd` (tmpfiles) and `networkDir` is created by lndinit/lnd as the lnd user — so lnd can replace `admin.macaroon` with a symlink to any root-only file. Root then reads it through the symlink (xxd does a plain `open`), hex-encodes it, and line 282 ships those bytes as the `Grpc-Metadata-macaroon` HTTP header to `https://restAddress:restPort/v1/macaroon` — a listener the compromised lnd itself controls. The content leaves the root context before any validation is possible (macaroon bytes are opaque; the onion-addresses read-once-validate pattern cannot apply). One root-only file is exfiltrated per service start; `Restart=on-failure` (spaced), deploys, and reboots all re-run the script.

The code's own comment (lnd.nix:265-274) states the threat model — "a compromised lnd escalates to arbitrary root file overwrite/chown" — and closes exactly the write direction while leaving the read direction open. Payoff targets: `backup-encryption-env` (PASSPHRASE decrypting backups that contain the entire secretsDir and `/var/lib/tor`, per `backups.nix` filelist), `wg-server-private-key` (impersonate/decrypt the operator's WireGuard tunnel that fronts the admin REST API), SSH host keys, `/etc/shadow`. This is the same class the maintainer already accepts as in-scope for this script.

Recommended fix: de-privilege the read so root never dereferences an lnd-owned path — e.g. `adminMacaroonHex=$(${runAsUser} lnd cat '${networkDir}/admin.macaroon' | xxd -ps -u -c 99999)` (fails closed: lnd cannot read root-only files through its own symlink), or open with `O_NOFOLLOW` + fstat-regular via a small helper. The staging/rename write path needs no change.
