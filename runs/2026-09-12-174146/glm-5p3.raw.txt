- **SECURITY.md guix.sigs claim**: true — pinned nixpkgs' bitcoind verifies SHA256SUMS against hash-pinned guix.sigs builder keys, fail-closed, in `preUnpack`.
- **Prior findings closure** spot-checked: M-2 (lndconnect no longer rebinds), M-3 (whitelist trimmed), M-4 (onion-addresses symlink privesc), L-6/L-7 (argv, quoting), wg re-exec RCE — all genuinely fixed, most with regression tests (including a symlink-canary test for the macaroon read path).

- Sweeps for risky patterns (0.0.0.0 binds, 777, eval/source, argv passwords, curl|bash): clean; the only 777 is an intentional test fixture.

## 4. Findings

No high or medium severity findings. The fork's own audit trail (three adversarial rounds, all resolutions verified present) holds up under independent re-review. Four low/informational items:

**F-1 (LOW)** — `modules/presets/wireguard.nix`: assertion gating is inconsistent. The nftables refusal fires unconditionally (because the iptables rules would silently vanish), but the firewall-enabled assertion only fires on the `lndconnect` path. With `lnd.lndconnect.enable = false`, `restrictPeer = true` (the default), and `networking.firewall.enable = false`, the preset evaluates cleanly while `restrictPeer` is silently inert — its documented contract ("prevent the peer from connecting to any addresses except the WireGuard server address") does not hold. Impact is low because a disabled firewall opens the whole node by the user's explicit choice, but the preset should either refuse or drop the `restrictPeer` promise when its rules cannot be installed.

**F-2 (LOW, known/deferred)** — the wireguard preset binds lnd's macaroon-admin REST API to `0.0.0.0` when lndconnect is enabled, relying solely on the firewall. This is tracked in `docs/wireguard-rest-bind.md` with a correct breakage analysis and a recommended second-listener design. Compensating controls verified present: firewall-enabled and anti-nftables assertions, interface+peer-scoped accept rule, restrictPeer inserted ahead of all accepts, release-gated VM test. Re-confirmed as the single highest-blast-radius design decision in the fork; the deferral is documented and defended, and the recommended `extraConfig` second-`restlisten` variant remains the right fix.

**F-3 (INFO)** — `helper/makeShell.nix`, `update-nix-bitcoin`: on first run (no existing `nix-bitcoin-release.nix`) the printed compare URL is malformed because the base commit is extracted from an empty string. Cosmetic; the operator is still told to review the commit.

**F-4 (INFO)** — `modules/bitcoind-rpc-public-whitelist.nix`: `deriveaddresses` permits up to 1,000,000 derivations per call (server-capped in Core v31.1, verified). Worst case is seconds-to-tens-of-seconds of CPU per call — bounded, but the largest per-call cost left in the list, and the fork's own bar excluded minutes-scale costs. Only relevant if the public RPC user is exposed beyond localhost, which the whitelist header already warns against.

Documented-by-design (not findings): operator holds full privileged bitcoind RPC via group `bitcoin` cookie access (L-10, warning comment in place); operator runs `lncli` as the lnd user; `wg-connect`/`lndconnect-wg` print the peer private key / admin macaroon QR to the operator terminal (pairing feature).
