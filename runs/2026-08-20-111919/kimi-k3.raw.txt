## Summary of the audit

I mapped the full attack surface: `modules/` (16 modules + presets + secrets + deployment), `pkgs/` (lib.nix hardening, netns-exec C wrapper, lndinit/nbxplorer packaging, fetchers), and `helper/` scripts. This fork has already had a serious audit pass (commits `e66c00a`, `8c2c342`, `6379e34`, etc.), and it shows: secrets are referenced by runtime path only, never interpolated into the store; the rpcauth password is passed via file, not argv; the onion-addresses symlink race is properly fixed (root-owned population, `chown -h`, symlink refusal); the lndconnect 0.0.0.0 footgun was removed; netns-exec validates its netns whitelist, requires absolute exec paths, and drops caps before exec; the lnd/electrs `requires` cascade was fixed with `wants`.

Things I checked and cleared: setup-secrets permission logic (dir 0751 + per-file 0440/owner is sound, no symlink window since the dir is root-only), bitcoind/lnd/nbxplorer/electrs preStart secret handling (all runtime-path reads, files 0600/0640 in 0770 dirs), nixops `chmod o+x` (per-file perms backstop it), the krops activation script (fail-closed, no injection), macaroon creation via fd-passed admin macaroon (correct), backups (encrypted, root-only passphrase), supply chain (all fetchers hash-pinned, krops pinned to a commit), and the netns iptables rules (fail-closed INPUT, correct allowlist).

Three findings remain, none critical:

1. **`setban` on the btcpayserver/nbxplorer RPC user** (btcpayserver.nix). The module itself documents the whitelist safety bar as "no P2P side effects" for the public user, then grants this user `setban`. A compromised nbxplorer is already a *whitelisted P2P peer* (it connects via `btcnodeendpoint` on `whitelistedPort`); combined with `setban` to knock out the node's honest outbound peers, that is a practical eclipse path against the bitcoind backing a funds-holding lnd. NBXplorer needs `getpeerinfo` (already inherited); I found no evidence it needs `setban` on modern bitcoind.

2. **`fundrawtransaction` in the public RPC whitelist.** It's a wallet method; the whitelist file's stated bar is "no leaks of wallet contents." bitcoind here is built/run with wallet support enabled (the module's `disablewallet` defaults to null), so if an operator ever loads a wallet via the privileged user, every holder of the public credentials (lnd, electrs, nbxplorer, i.e. any one compromised service) can enumerate wallet UTXOs and change addresses through crafted `fundrawtransaction` calls. Privacy leak only; signing/spending methods are not whitelisted.

3. **netns mode exposes unauthenticated ZMQ (and the Tor SOCKS port) to every local user via the bridge IP.** `rpc.allowip` and the netns INPUT chain both allow `bridgeIp`, which is the source address of *any* host-local process reaching the netns. RPC is still auth-gated, but ZMQ (`tcp://169.254.1.12:28332/28333`) has no auth, so any unprivileged local user can subscribe to the node's raw block/tx stream, and any local user can use the node's Tor SOCKS at `169.254.1.10:9050`. Small privacy exposure, fail-open in the wrong direction.
