## Summary of investigation

**Attack surface mapped.** Modules handling funds/keys/root: `bitcoind.nix` (RPC creds, cookie, wallet), `lnd.nix` (macaroons, TLS key, wallet seed/password, a root `ExecStartPost`), `btcpayserver.nix`/`electrs.nix` (RPC consumers), `secrets/secrets.nix` (all secret perms), `onion-addresses.nix` (root+DAC_OVERRIDE hostname copier), `operator.nix` (sudo/doas), `netns-isolation.nix`, `pkgs/lib.nix` (systemd hardening).

**What I checked and ruled out (with reasons):**
- *Secrets into the Nix store*: all service configs (`bitcoin.conf`, `lnd.conf`, nbxplorer/btcpay config) use `builtins.toFile`/`writeText` with only non-secret content (usernames, addresses, paths); secrets are appended at runtime in `preStart`. Clean.
- *Secret file perms*: `secrets.nix` uses `escapeShellArg`, dir `0700`→`0751` (other gets `--x` only), per-file `440` with `group=user`. Cookie group-read is operator-only (only `operator` joins group `bitcoin`; lnd/electrs/nbxplorer are in `bitcoinrpc-public`, not `bitcoin`). Clean.
- *RPC whitelist*: `bitcoind-rpc-public-whitelist.nix` explicitly excludes wallet/DoS methods with audit-trail comments; `getpeerinfo`/`getnodeaddresses` kept only because lnd requires them and the user is local-by-default. Reasonable.
- *onion-addresses symlink privesc* (the historical bug): heavily hardened — refuses symlinked hostname src, builds per-user dirs as `root:root 0700` and chowns last, `chown -h`, dataDir not a symlink, `StateDirectoryMode=771` so "other" can't create entries. Clean.
- *Supply chain*: `lndinit`/`nbxplorer` use `fetchFromGitHub` with pinned hashes; flake inputs pinned; `overrides.nix` empty; `helper/fetch-release` now refuses to fetch upstream unless explicitly overridden. Clean.
- *lnd `wants` vs `requires`*: the cascade-stop fix is correct and the comments document the ordering invariant.
- *bitcoind-remote preset*: `mkForce postStart=""` is fine (no local bitcoind → no cookie).

**Where the bug is.** Commit `9b71bec` ("symlink-safe" macaroon creation) places the `mktemp` temp file inside `$RUNTIME_DIRECTORY` (`/run/lnd`), which is owned by the untrusted `lnd` user with mode `0711` and **no sticky bit**. The lnd user can therefore `unlink` the root-owned temp file and replace it with a symlink in the window before the root script's `chmod`/`chown`/redirection act on it. The commit's own claim — "the chown only ever touches our own temp file" — is false, because lnd controls the directory. I confirmed `umask ug=r,o=` is harmless (yields mode 0400) and that only lnd uses the `rootScript` pattern, so this is the one root-writes-through-service-writable-path defect. I could not run the inotify race empirically (`inotifywait` absent from this sandbox), so I rate confidence conservatively and describe both the reliable primitive (chown/chmod-as-root via a lnd-controlled `curl` delay) and the likely-winnable one (arbitrary write as root → RCE).
